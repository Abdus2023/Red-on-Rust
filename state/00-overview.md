## 1. Authority chain (this directory adds no normative content)

```
frozen normative sources (Red-on-Rust.md; frozen addenda inside spec/01)
  -> authoritative registers (spec/01…09, req/registry.json, check.py
     registration, term/, state/dispositions.json)
  -> deterministic generators (spec/_build_index.py, final/_build.py,
     reg/_compile.py, term/_dict.py, state/_project.py)
  -> derived artifacts (spec/10, final/*, reg/*, term/*, state/01…02,
     state/repository-state.json)
  -> cross-artifact consistency gates (state/_project.py battery; the other
     check.py checkers)
  -> repository-state projection (state/01; state/repository-state.json)
```

No generated document in this directory is a second source of truth: where a
projection and an authority differ, the authority governs **and the gate
fails**. Historical evidence ≠ current authority; derived projection ≠
normative source; repository integrity ≠ semantic verification.

## 3. What the gate checks (V-08; fail-closed)

1. **U registry vs every U projection** — spec/09 rows vs the spec/09 status
   declaration, spec/10, final/09 §A (counts *and* per-row status), and this
   directory's projection. A resolved U-item flipped to OPEN in any derived
   projection fails the build.
2. **Cardinality vs numeric range** — registered-record cardinality (39) and
   numeric identifier maximum (U-45) are separate facts; numbering gaps are
   recorded as gaps and contiguity is never required nor asserted.
3. **Checker inventory vs checker projections** — the inventory is derived
   from the `check.py` registration (ast, no execution) and independently
   re-globbed; the FINAL1 current-count projections (final/00, final/08) must
   carry the derived counts. Historical counts survive only where explicitly
   marked historical (see `02` DISP-08/DISP-14).
4. **Canonical tag set vs index** — spec/08 §1's two tables are the authority;
   the spec/10 indexed set must equal them; documented aliases
   (MARSHAL-CAPABILITY-REJECT ≙ MARSHAL-NO-RAW-CAPABILITY) must not be
   indexed. `spec/_build_index.py` enforces the same at generation time.
5. **Requirement and atomic registries** — five-authority ID identity
   (spec/01, spec/03, spec/10, final/03, reg), all-SPECIFIED statuses, atomic
   record count vs `req/registry.json` and the final/03 atomic-layer line.
6. **Mutation registry** — spec/08 §2 vs spec/10, dense M001…M042.
7. **Canonical predicate agreement (V-05)** — R-CORE-02's chain must have
   `ValidatedRequest(E)` as its first conjunct over R-CORE-11's signatures,
   the subsumption `ValidatedRequest(E) ⇒ ValidatedPlan(plan(E))` must be
   present, and every current-state projection (spec/01, spec/00 §4, README
   box, spec/10, final/01, final/05 GI-SEC-02, reg) must agree; the
   `ValidatedPlan(P) ∧` form may survive only in historical/authority records.
8. **Dispositions (V-06)** — every resolved U-item covered by a RESOLVED
   disposition; authority tokens resolve; protected historical snapshots
   hash-verified (editing an audit is a provenance violation until its
   disposition record is deliberately updated).
9. **Evidence discipline** — claims stay 0/0/0/0; REF1 and V1 stay
   CONDITIONAL; implementation stays BOOTSTRAP; ceiling stays SPECIFIED.
10. **Validation pins** — computed values are compared with the EXPECTED block
    inside `state/_project.py` (in the style of `reg/_compile.py`'s
    `EXPECTED_COUNT`); a mismatch is an INVESTIGATE failure, never a re-base.

A PASS of this gate is repository-integrity evidence only — never semantic
verification of any `R-…` obligation (V1 F-INFL-01), and never evidence of
implementation, testing, verification or proof (R-CLAIM-01).
